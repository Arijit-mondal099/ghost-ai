## Architecture Decisions

- shadcn is installed with the new `radix-nova` preset and the consolidated `radix-ui` package (no individual `@radix-ui/react-*` packages). Components are generated into `components/ui/` at the project root (no `src/`).
- Dark is the only mode. `globals.css` sets the same dark palette on both `:root` and `.dark` so shadcn's `dark:` variants and the default-light classes resolve to the same dark values. `<html>` carries the `dark` class permanently.
- The shadcn variable names (`--background`, `--primary`, etc.) and the project's variable names (`--bg-base`, `--text-primary`, `--accent-primary`, etc.) coexist in `:root` so generated components and app-level code can each use their preferred naming without conversion.
- `components/ui/*` are treated as protected third-party foundation components. Project-specific styling lives in `app/`, `components/` (composables), or future feature-level wrappers — never inside the generated shadcn files.
- The shadcn `DialogContent` hardcodes `rounded-xl` and `bg-popover` in its className argument. The editor's `EditorDialog.Content` re-implements the same surface with project defaults (`rounded-3xl`, `bg-base`) applied — preserving animations and `showCloseButton` behavior. This is the pattern for any future shadcn primitive that needs project-style overrides without modifying the protected primitive.
- Clerk uses the `shadcn` theme from `@clerk/ui/themes` (not the `dark` theme), because the project has shadcn installed. The `shadcn` theme is a prebuilt appearance that reads the standard shadcn CSS variable namespace (`--card`, `--card-foreground`, `--primary`, `--foreground`, `--muted`, `--input`, `--border`, `--ring`, `--destructive`, etc.) — these are already declared in `app/globals.css` `:root` and `.dark` with the project's dark hex values, so the theme inherits the dark palette automatically. The matching `@import "@clerk/ui/themes/shadcn.css"` line in `app/globals.css` (alongside the existing Tailwind imports) is what actually emits the shadcn-token-mapped classes into the bundle. Without that import, Clerk's "Manage account" / profile pages fall back to light defaults. **Do NOT override the `variables` block in the Clerk appearance with project-specific token names** (e.g. `--bg-base`, `--accent-primary`) — the per-component `appearance.variables` block **replaces** the theme's defaults rather than merging, so referencing non-shadcn variable names there causes UserProfile/AccountSettings to lose their shadcn-themed colors. Keep the `variables` block minimal (only `fontFamily` or similar non-conflicting keys) and put project-specific styling in the `elements` block instead, which is composable.
- The `<UserButton>`'s appearance only propagates to the **popover menu** by default — the "Manage account" modal it opens (rendered as a separate `<UserProfile>` component) needs the same appearance passed via the `userProfileProps={{ appearance: ... }}` prop. Without this, the popover renders dark (correct) but the user-profile modal inside it falls back to Clerk's default light theme. The fix in `components/editor/editor-navbar.tsx` passes `authAppearance` to both the `appearance` prop and `userProfileProps.appearance` so the modal inherits the same theme.
- Next 16 renamed Middleware to Proxy — `proxy.ts` at the project root is the new convention. The function inside is still `clerkMiddleware` from `@clerk/nextjs/server`; only the file name and the documented "Proxy" terminology changed.
- The `ClerkProvider` in `@clerk/nextjs@7` is an async Server Component (`Promise<React.JSX.Element>`), so `RootLayout` is declared `async`. No client wrapper needed. Each Clerk surface (`<SignIn>`, `<SignUp>`, `<UserButton>`) receives the shared `authAppearance` per-instance, so the provider itself stays unopinionated and per-component `elements` overrides apply where needed.
- Spec 04 introduced the first `hooks/` directory at the project root, matching the `components.json` alias `@/hooks`. Feature-specific hooks (e.g. `useProjectDialogs`) live here; cross-cutting state primitives will land in `lib/` if they emerge. The hook colocates dialog state, form state, and the project list so the editor page is the single mount point for all three dialogs and the home CTA + sidebar CTA can share the same open handler.
- shadcn `Input` has no explicit text color and uses `bg-transparent`. Against a non-default background (e.g. inside `EditorDialog.Content` which is `bg-base`), the entered text + placeholder render nearly-invisible because native `<input>` color inheritance is unreliable. The established fix is to set `className="bg-surface text-copy-primary placeholder:text-copy-muted"` per consumer — gives a clear visual boundary, high-contrast text, and a de-emphasized but readable placeholder. The `Input` primitive itself is left untouched per the protected-foundation rule.
- **API route convention (spec 06):** every `app/api/*` route is auto-protected by `proxy.ts` via its `(api|trpc)(.*)` matcher, but the handler still calls `auth()` and returns a 401 explicitly — defense in depth and a clear per-route contract. All errors are `{ error: { code, message } }` with `Content-Type: application/json`; success payloads are returned bare (no `{ data }` wrapper). The trio `lib/api/responses.ts` + `lib/api/auth.ts` + `lib/api/validation.ts` is the single source of truth for status helpers, the `requireUserId()` wrapper, and hand-rolled allow-list body parsing. Handlers should be thin (~20 lines of orchestration) and lean on these helpers — no inline `Response` construction outside the helpers. The two-step find-then-mutate pattern (find by id for `ownerId` → ownership check → mutate) is the established way to preserve the 403-vs-404 distinction the spec requires. Dynamic-segment handlers use Next 16's globally-typed `RouteContext<'/api/...'>` and `await ctx.params` — `next typegen` must be run before `tsc` to materialize the type.
- **Cuid IDs are generated at the Prisma client layer, not the database.** `Project.id` declares `@default(cuid())` in `prisma/models/project.prisma`; the migration SQL omits a `DEFAULT` clause because Prisma generates the cuid before INSERT. Route handlers pass `data: { ownerId, name }` and never set `id` themselves. The same pattern applies to any future model with `@default(cuid())`.
- **Spec 07 — server-component / client-child split for the editor home.** `app/editor/page.tsx` is now an `async` server component that calls `getProjectsForCurrentUser()` and passes a plain `Project[]` to `<EditorHomeClient>` (a new `app/editor/editor-home-client.tsx` client component). The client child owns the sidebar `useState`, mounts the three dialogs, and instantiates `useProjectActions(initialProjects)`. This is the established pattern when a route needs both server-side data fetching and client-side interactivity — the boundary lives at the page level, not at the data helper. Server components fetch; client components mutate and own state. The `Project` interface stays JSON-serializable (no `Date` or other non-serializable fields) so the server-to-client prop is a plain array.
- **Spec 07 — `useProjectActions` is a derived-state hook, not a store.** The old `useProjectDialogs` owned the project list in `useState` and mutated it on every `submit*`; the new `useProjectActions(initialProjects)` derives `ownedProjects` / `sharedProjects` from the input prop on every render and never mutates local state. The three `submit*` handlers call `fetch` + `router.refresh()` instead — the next render re-reads the server data through the page prop. This is the established pattern for server-driven lists: the source of truth is the database, the hook is just a UI-state owner (dialog open/close + form + submitting flag). Same consumer API as the old hook, so the three dialogs and the page didn't need to change.
- **Spec 08 — workspace access collapses 404 + 403.** `getAccessibleProject` returns one `null` for missing and unauthorized because both render the same `AccessDenied` surface. Page components use the `PageProps<"/editor/[roomId]">` global (not `RouteContext<>`, which is API-routes-only). Navbar extension is additive optional slots (`center`, `rightActions`) so home renders unchanged. Sidebar rows are links with the dropdown trigger as a sibling — never nest the trigger inside the link.
- **Spec 09 — collaborators are email rows + Clerk enrichment, no local user table.** `ProjectCollaborator(email)` is the join key (lowercased everywhere: validator → DB → Clerk match). `findUserByEmail` returns `null` on miss (invite gate depends on it); `enrichCollaborators` returns email-only stubs on miss (list fallback depends on it). `isOwner` is computed server-side (`project.ownerId === identity.userId`) and passed as a prop — the client never decides it. `@@unique([projectId, email])` → `P2002` → `409 ALREADY_COLLABORATOR` is the authoritative duplicate signal (no pre-check race). `clerkClient()` is async in `@clerk/nextjs@7` and `getUserList({ emailAddress })` is partial-match, so the exact-match post-filter is the real gate.
- **Spec 10 — Liveblocks identity model.** `liveblocks.config.ts` keeps `Storage: {}` — the graph is owned by `useLiveblocksFlow`'s `flow` LiveObject (default `storageKey: "flow"`); `useCanvasDrop` reaches it via a local LSON cast, generic over `CanvasNode`/`CanvasEdge`. Presence is `{cursor, isThinking}`; cursor color is a deterministic djb2 hash (`cursorColorForUserId`) so reconnects keep the same hue. Auth route uses project id as room id and `getOrCreateRoom` with `room:write` default — token issuance is the second layer, project access the first.
- **Canvas — Liveblocks write paths.** Inserts go through `LiveObject.from(node)` + `LiveMap.set` in `useCanvasDrop` (mirrors the package's own `add` path). Moves/resizes flow through `onNodesChange` (`position`/`dimensions` cases in `dist/lib/flow.js`); connects through `onConnect` (`addEdge` + `edges.set`); deletes MUST go through `onDelete` (`maps.delete`) — `remove` changes are an intentional no-op in the package. Selection (`selected`) / `dragging` / `measured` / `resizing` are local-only (`false` in `NODE_BASE_CONFIG`), so hover/selection never leaks across clients.
- **Canvas — node/edge UX contracts.** One `canvasNode` type with `data.shape` driving the visual (not six node types) keeps Storage stable across shape work. Handles: 10px white dots, hidden until hover/selected, stable `top`/`left` target + `right`/`bottom` source ids under `ConnectionMode.Loose`. Edges: `interactionWidth={20}` for clickability, selected stroke brightens. Resize: `NodeResizer` only when selected, per-shape floors, circle keeps aspect ratio.
